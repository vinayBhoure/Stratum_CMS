# Error: Prisma P1000 — Authentication Failed Against Docker PostgreSQL

**Date:** 2026-05-14
**Layer:** Database / Infrastructure
**Severity:** Critical (blocks all DB operations)

---

## Error Message
```
Error: P1000: Authentication failed against database server,
the provided database credentials for `vinay` are not valid.

Please make sure to provide valid database credentials for
the database server at the configured address.
```

Triggered by:
```bash
cd server && npx prisma migrate dev --name init
```

---

## Context
- Setting up local PostgreSQL via a Docker container (`postgres:17`)
- Container had port `5432` mapped to `localhost:5432`
- `DATABASE_URL` in `.env`: `postgresql://vinay:password123@localhost:5432/mydb`
- Credentials matched the container env vars (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`)
- Connection worked fine **inside the container** (`docker exec ... psql -U vinay`) but failed from the host

---

## Root Cause

Two compounding issues:

### 1. Auth method mismatch (`md5` vs `scram-sha-256`)
The default `pg_hba.conf` generated by `postgres:17` Docker image uses `md5` for host connections:
```
host all all 0.0.0.0/0 md5
```
However, PostgreSQL 17 stores passwords using `scram-sha-256` by default (`password_encryption = scram-sha-256`).
The `md5` auth method cannot verify a `scram-sha-256` password hash, so all TCP connections fail even with correct credentials.

### 2. IPv6 loopback not covered
On Windows, `localhost` resolves to `::1` (IPv6 loopback), not `127.0.0.1`.
The `pg_hba.conf` only had `0.0.0.0/0` which covers IPv4 only.
IPv6 connections had no matching rule and were silently rejected.

---

## Resolution

### Fix `pg_hba.conf` inside the container
```bash
docker exec postgres-db bash -c "printf 'host all all 0.0.0.0/0 scram-sha-256\nhost all all ::/0 scram-sha-256\nlocal all all trust\n' > /var/lib/postgresql/data/pg_hba.conf"
```

### Reload PostgreSQL config (no restart needed)
```bash
docker exec postgres-db psql -U vinay -d mydb -c "SELECT pg_reload_conf();"
```

### Verify the fix works
```bash
PGPASSWORD=password123 psql -h localhost -U vinay -d mydb -c "SELECT 1;"
# Expected: (1 row)
```

### Final `pg_hba.conf` content
```
host all all 0.0.0.0/0 scram-sha-256
host all all ::/0 scram-sha-256
local all all trust
```

---

## Code Change
```diff
- host all all 0.0.0.0/0 md5
+ host all all 0.0.0.0/0 scram-sha-256
+ host all all ::/0 scram-sha-256
  local all all trust
```

---

## Prevention

### If you recreate the Docker container
Pass `pg_hba.conf` as a mount or init script so the correct auth method is set from the start:
```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: vinay
      POSTGRES_PASSWORD: password123
      POSTGRES_DB: mydb
    volumes:
      - ./docker/pg_hba.conf:/etc/postgresql/pg_hba.conf
    command: postgres -c hba_file=/etc/postgresql/pg_hba.conf
```

With `docker/pg_hba.conf`:
```
host all all 0.0.0.0/0 scram-sha-256
host all all ::/0 scram-sha-256
local all all trust
```

### General rules
- On Windows, always include `::/0` in `pg_hba.conf` — `localhost` routes via IPv6
- Always match `pg_hba.conf` auth method to PostgreSQL's `password_encryption` setting
- PostgreSQL 14+ defaults to `scram-sha-256`; don't use `md5` with modern images

---

## Final Resolution (Adopted)

After extensive debugging, the TCP connection between the Windows host and the Docker container had an additional unresolved network routing issue (likely Docker Desktop WSL2 networking). The decision was made to **switch to Neon DB** (serverless cloud PostgreSQL) and remove the Docker dependency entirely.

**DATABASE_URL updated to Neon direct endpoint:**
```
postgresql://neondb_owner:<password>@ep-red-leaf-aq4wd3pb.c-8.us-east-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require
```

Migration ran successfully on first attempt against Neon DB.
